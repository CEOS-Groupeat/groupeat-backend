# 검색 API 성능 개선

검색 조건에 따라 병목을 구분하고, SQL 실행 계획과 k6 부하 테스트로 개선 효과를 검증했다.

## 실험 환경

- MacBook Pro M1, 로컬 Spring, Docker PostgreSQL 16
- k6: 100 VU, 요청 사이 대기 0.2초
- 준비 60초 → 본 측정 120초 → 종료 15초
- DB 연결 풀 최대 10개
- 커서 없는 첫 페이지, 반환 20개
- 전체 가게 10,002개
- 본 측정 처리량 = 본 측정 요청 수 ÷ 120초

## 1. 키워드 검색: 불필요한 DISTINCT 제거

### 문제와 해결

가게 데이터 증가 후 키워드 검색의 응답 지연과 DB 연결 대기가 증가했다.

실행 계획에서 스케줄 JOIN이 없는 단일 테이블 조회에도 DISTINCT가 적용되어
전체 정렬과 중복 제거가 수행되는 것을 확인했다.

**스케줄 JOIN이 없는 목록 조회에서만 DISTINCT를 생략**했다.
스케줄 조건 검색의 DISTINCT와 전체 개수 쿼리는 유지했다.

### 결과

SQL 비교 3회의 실행 시간 중앙값은 30.178ms → 9.006ms로 감소했다.
정렬 방식은 quicksort에서 top-N heapsort로 바뀌었고,
정렬 메모리는 3,699kB → 35kB로 감소했다.

검색 조건: `keyword=검색실험`, `sortType=NONE`, `size=20`
검색 일치 가게: 10,000개

| 지표 | 개선 전 | 개선 후 1회 | 개선 후 2회 |
|---|---:|---:|---:|
| 평균 응답 시간 | 306.65ms | 20.51ms | 27.63ms |
| p95 | 399.00ms | 43.64ms | 84.90ms |
| p99 | 549.04ms | 92.30ms | 145.63ms |
| 본 측정 처리량 | 196.9 RPS | 451.7 RPS | 437.5 RPS |
| 응답 검증 실패율 | 0% | 0% | 0% |

개선 후 두 실행에서 **p95 78.7~89.1% 감소**, **처리량 2.22~2.29배 증가**를 관찰했다.
전후 실행 날짜가 달라 개선율은 해당 실험의 관측 범위로 제시한다.

## 2. 스케줄 조건 검색: 인덱스와 실행 계획 개선

### 실험 과정

1. **EXISTS 전환 검토**
    - JOIN + DISTINCT와 비교했으나 해당 조건에서 실행 시간 개선이 없어 미채택했다.

2. **요일 부분 인덱스 추가**
    - 삭제되지 않고 사용 가능한 스케줄을 요일 기준으로 탐색하도록 구성했다.
    - 목록 SQL: 27.167ms → 15.507ms
    - 개수 SQL: 21.931ms → 14.306ms
    - 그러나 API 평균 응답 시간은 약 1초로 유지됐다.

3. **실제 API 실행 계획 추적**
    - auto_explain으로 반복 요청 100회를 확인했다.
    - 해당 로그에서 9번째부터 Generic 계획으로 전환되며 새 인덱스를 사용하지 않았다.
    - 기존 인덱스로 주문·요일 스케줄을 각각 10,000번 반복 조회했다.
    - 전환 시점은 이번 관찰값이며 고정 규칙은 아니다.

4. **Custom 계획 적용**
    - 전체 연결에 Custom 계획을 강제해 성능 개선을 확인했다.
    - 이후 전체 연결 설정을 제거하고 검색 트랜잭션에서만 아래 명령을 실행하도록 변경했다.

```sql
SET LOCAL plan_cache_mode = force_custom_plan;
```

목록·개수 조회에 적용되며 커밋·롤백 후 이전 설정으로 복원된다.
현재 해당 검색 서비스 경로의 키워드 단독 검색도 적용 대상이다.

### 결과

검색 조건:
- `keyword=검색실험`, `sortType=NONE`, `size=20`
- `pickupDate=2026-10-08`, `pickupTimes=12:00:00`, `quantity=50`
- 전체 검색 결과 2,000개

아래 세 경우 모두 요일 부분 인덱스가 있는 상태다.

| 날짜 | 계획 설정 | 평균 | p95 | 본 측정 처리량 |
|---|---|---:|---:|---:|
| 2026-10-02 | 기본 설정 | 1,060ms | 1,270ms | 78.87 RPS |
| 2026-10-02 | 전체 연결 Custom | 212.63ms | 339.95ms | 241.38 RPS |
| 2026-10-05 | 검색 트랜잭션 Custom | 193.53ms | 328.71ms | 253.45 RPS |

- 같은 날 비교: **평균 79.9% 감소**, **p95 73.2% 감소**, **처리량 3.06배 증가**
- 최종 구현의 반복 요청 100회에서 목록·개수 모두 요일 인덱스 사용
- 위 부하 테스트 모두 응답 검증 실패율 0%

10월 5일은 최소 준비 일수 조건이 달라졌으므로,
추가 성능 향상보다는 최종 구현의 성능 유지 확인으로 해석했다.

## 실행 방법

프로젝트 루트에서 실행한다.

```bash
k6 run performance/search-load.js
```

현재 `search-load.js`는 스케줄 조건 검색용이다.
키워드 단독 검색은 스케줄 파라미터를 제외하고,
해당 데이터의 예상 결과 개수로 검증하도록 별도 스크립트를 구성해야 한다.

실행 전:
- 로컬 API와 DB, 실험 데이터를 준비한다.
- BASE_URL, 검색 조건, EXPECTED_TOTAL을 확인한다.
- 스케줄 검색의 픽업일은 실행 시점에 유효한 날짜인지 확인한다.
- 단일 요청으로 예상 결과를 검증한다.
- auto_explain 및 상세 SQL·바인딩 진단 로그를 끈다.

## 해석 범위

- 두 실험은 검색 조건과 변경 사항이 다르므로 개선율을 합산하지 않는다.
- 키워드 검색 수치는 DISTINCT 개선 당시 결과이며,
  최종 Custom 설정까지 적용한 코드의 재측정 결과는 아니다.
- 로컬 첫 페이지·기본 정렬·100 VU 중심의 검증으로 운영 최대 처리량을 뜻하지 않는다.
- 다른 정렬·연속 페이지·다양한 조건·혼합 부하는 별도 검증 대상이다.
